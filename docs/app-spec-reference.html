App spec reference

An app spec is one JSON file that describes a BAW process app: its name, the data it collects, the screens, the review and confirmation, and how it looks. create_app (or generate_app.py) turns it into an installable .twx. This page lists every key, what it does and the rules the generator checks.

What a spec becomes

One spec builds one process app with one client-side human service, exposed as a URL so users can launch it. The service has one coach (screen) per step, then an optional review and an optional confirmation:

  1. Start
  2. →
  3. Initialize
  4. →
  5. Step 1 … Step N
  6. →
  7. Review
  8. →
  9. Assign reference
  10. →
  11. Confirmation
  12. →
  13. End
  • Initialize creates the business object, sets every checkbox to false and clears the reference number.
  • Steps each get a Next button, and a Back button from step 2 on. With "layout": "tabs" all steps become tabs of a single screen.
  • Review (dashed: optional) shows every answer read-only, with Back and Submit.
  • Confirmation (optional) shows a generated reference number and the fields you pick.

Every screen is built from standard UI Toolkit views bound to one business object, so the app runs as soon as it is installed, and inspect_coaches and modernize_app work on it like on any other app.

Where specs live

Write your spec as work/<ACRONYM>.app.json. The work/ folder is not committed. The examples in app-specs/ are committed; copy one rather than editing it.

A minimal spec

This is a complete, valid spec: one step, three fields, and the default review screen.

{
  "app": { "name": "ZZ Leave Request", "acronym": "ZZLEAVE", "snapshot": "1.0.0" },
  "businessObject": { "name": "LeaveRequest", "variable": "leave" },
  "service": { "name": "Leave Request" },
  "steps": [
    {
      "title": "Your leave",
      "fields": [
        { "name": "employeeName", "label": "Employee Name", "required": true },
        { "name": "firstDay", "label": "First Day", "type": "Date" },
        { "name": "days", "label": "Number of Days", "type": "Integer" }
      ]
    }
  ]
}

Check a spec without touching the server. The generator validates the whole spec first and lists every problem at once; it only contacts the server after the spec is valid.

python3 server/generate_app.py work/ZZLEAVE.app.json work/ZZLEAVE-1.0.0.twx
A valid spec goes on to build

When the spec is valid, the command builds the .twx. The first build ever also downloads the Hiring Sample (HSS) once into work/base-HSS.twx to package the app, so it needs your .env. Building does not install anything; installing is a separate step.

app, businessObject, service

"businessObject": { "name": "LeaveRequest", "variable": "leave" },
"service": { "name": "Leave Request", "description": "Ask for time off." }
KeyRuleExample

service.nameRequired. What users see, and what you pass to test_serviceLeave Request
service.descriptionOptional. Defaults to the service name

Naming rules that protect the server

  • ZZ only. install_app refuses any app whose name does not start with "ZZ" or whose acronym does not start with ZZ. The generator itself accepts other names, so the check happens at install.
  • New acronym for a new app. Run list_apps (or python3 server/baw_ops.py list) first. If the acronym belongs to another app, the install fails.
  • New snapshot name for every change. BAW silently keeps the old content when a snapshot name is reused, so create_app and install_app refuse a name that already exists. Bump it: 1.0.0 → 1.0.1 or 1.1.0.
  • Same acronym, new snapshot = update. When the app already exists, create_app builds the spec as a new snapshot of that app, so its run URL and history stay.

layout and form

"layout": "steps" (default)

One screen per step, titled "Step 2 of 3: <title>" when there is more than one step. Back and Next move between them. The last step's button says Next when a review follows, otherwise Submit.

"layout": "tabs"

One screen with a tab per step. Users move freely between tabs, then one button leaves the screen for the review (or the end). Step intro and step button labels are not used; set them in form.

form is read only with "tabs":

KeyDefaultWhat it does
form.titleservice.nameTitle of the tabbed screen
form.intrononeText under the title
form.nextLabelNext, or Submit when "review": falseText of the button that leaves the screen
form.cancelLabelnoneAdds a button with this text that ends the service
 
"layout": "tabs",
"form": { "title": "New Quote", "nextLabel": "Submit", "cancelLabel": "Cancel" }

steps

A list, in order, with at least one step. Each step lists its fields directly (shown in one panel titled like the step) or its sections (several titled panels).

KeyRequiredWhat it does
titleYesScreen title (or tab name with "tabs")
introNoText under the title. "steps" layout only
fieldsOne of the twoThe step's fields, in one panel
sectionsOne of the twoTitled panels, each with its own fields and columns. When both are given, sections wins
columnsNoWith fields: 1 to 6 columns (default 1)
widthsNoWith fields: relative column widths, one number per column
nextLabelNoText of the forward button (default Next, or Submit on the last step without a review)
backLabelNoText of the Back button (steps 2 and later)
cancelLabelNoAdds a button with this text that ends the service
 
"steps": [
  { "title": "Requester", "intro": "Who needs the equipment?", "fields": [ ... ] },
  { "title": "Item", "nextLabel": "Continue", "cancelLabel": "Cancel", "fields": [ ... ] }
]

sections and columns

A section is a titled panel. Use sections when a step has more than about six fields.

KeyRequiredWhat it does
titleYesPanel title
introNoText at the top of the panel
columnsNo1 to 6, default 1
widthsNoOne positive number per column, relative to each other: [1, 1.6, 1] makes the middle column 1.6 times as wide
fieldsYesAt least one field

How fields fill the columns

Row by row (default)

Fields fill the columns left to right, then the next row. With 2 columns, fields 1 and 2 share the first row.

1234wide56

Placed by column

Give every field in the section a "column" (1, 2, …). Each column lists its fields top to bottom, in spec order, so columns can have different lengths.

A1B1A2B2A3
  • "wide": true puts a field on its own full-width row, between the column rows. Wide fields do not need a column.
  • On screens narrower than 900px the columns stack.
  • The content is 960px wide. With a theme, it grows to 1400px when any section has more than 3 columns, and theme.width sets it exactly.
{ "title": "Company", "columns": 2, "fields": [
  { "name": "legalName", "label": "Legal Name", "required": true },
  { "name": "taxId", "label": "Tax ID", "required": true },
  { "name": "supplierType", "label": "Supplier Type", "type": "Select", "options": ["Manufacturer", "Distributor"] },
  { "name": "yearEstablished", "label": "Year Established", "type": "Integer" },
  { "name": "businessSize", "label": "Business Size", "type": "Radio", "options": ["Small", "Medium", "Large"], "wide": true }
]}

fields

Each field becomes a property of the business object and an input on the screen.

KeyRequiredWhat it does
nameYesAn identifier, unique across all steps. referenceNumber is reserved when there is a confirmation
labelYesThe text shown next to the input
typeNoOne of the field types; default String
optionsSelect and RadioThe choices: a list of strings, or of {"value", "label"} when the stored value differs from the text shown
requiredNotrue shows the required marker. It is a visual marker only; the generated service has no validation, so it does not stop Next
helpNoAdds a help icon with this text
wideNotrue: full width in a multi-column section
columnNo1, 2, …: the column it sits in. All or none of a section's non-wide fields
iconNoIcon in the box before the input, with theme.fieldIcons. See the icon list
 
{ "name": "priority", "label": "Priority", "type": "Radio", "options": ["Low", "Normal", "High"] }
{ "name": "costCentre", "label": "Cost Centre", "type": "Select",
  "options": [ { "value": "CC100", "label": "100 - Finance" }, { "value": "CC200", "label": "200 - IT" } ] }
{ "name": "email", "label": "Email", "required": true, "help": "We send the decision here.", "icon": "mail" }

review and confirmation

review

On by default, titled "Review and Submit". It shows a read-only panel per step, a Back button to the last step and a Submit button.

ValueResult
left out, or trueReview screen with the default texts
{ "title", "intro", "submitLabel" }Review screen with your title, intro and Submit text
falseNo review. The last step (or the tabbed screen) submits directly

confirmation

Off unless present. After Submit, the service gives the request a reference number and shows it with the fields you list.

KeyDefaultWhat it does
titleSubmittedScreen title
messagenoneText under the title
referencePrefixREF-The reference number is this prefix plus the last 8 digits of the submit time in milliseconds, e.g. EQ-52814630. It is not checked for uniqueness
showFieldsnoneField names to show under the reference number. Each must be a field of the spec
 
"review": { "title": "Review your request", "submitLabel": "Send" },
"confirmation": {
  "title": "Request Submitted",
  "message": "Your request was sent to your manager.",
  "referencePrefix": "EQ-",
  "showFields": ["employeeName", "itemType"]
}

banner

Optional. A strip in the primary colour that replaces the plain title on every screen. It shows, left to right: the logo, the title, the product name and a short text. Unknown keys are rejected.

KeyWhat it does
titleBanner title. Default: the screen's own title, so each screen keeps its name
productLarge product name, e.g. QUOTE DESK
textShort text on the right, e.g. a greeting
logoPath to an image inside the project, relative to the project folder, e.g. work/logo.png. PNG, JPG, GIF, WebP or SVG, at most 200 KB. It is embedded in the app, so the server needs no access to the file
 
"banner": { "product": "QUOTE DESK", "text": "Good afternoon", "logo": "work/quote-logo.png" }

To cut a logo out of a screenshot, ask the agent to use crop_image; it writes the cut-out into work/.

Validation errors

The generator checks the whole spec and lists every problem before it builds anything. A real run on a spec with five mistakes:

$ python3 server/generate_app.py work/bad.app.json work/bad.twx
Invalid app spec:
  app.acronym must be 2-8 upper-case letters or digits, starting with a letter
  step 1: field name 'start date' must be an identifier
  step 1: field 'kind' (Select) needs options: a list of strings or {"value", "label"}
  step 1: field 'days' has unknown type 'Number'; use one of String, Text Area, Date, Boolean, Integer, Decimal, Select, Radio
  confirmation.showFields: unknown field 'reason'
Message containsFix
must be an identifierUse letters, digits and _ only, no spaces, not starting with a digit: startDate
is used twice (or is reserved)Rename one of the fields; names are shared by all steps. Do not name a field referenceNumber when there is a confirmation
needs optionsAdd "options": [...] to the Select or Radio field
needs a column from 1 to NOne field in the section has a column, so all non-wide fields need one
widths must list N positive numbersGive exactly one width per column
is not a theme settingCheck the spelling against the theme keys; they are case-sensitive
banner.logo … must be an image file inside the projectSave the image under the project folder (e.g. work/) and give the path relative to it
Snapshot … already existsFrom create_app or install_app: bump app.snapshot
Refusing to install intoFrom install_app: the name and acronym must both start with ZZ

What a spec cannot express

A spec builds forms. These need something else:

  • Tables, file uploads, links and menus. Add them in a React screen with the coach-modernize skill.
  • Validation and rules. No required-field blocking, no field-to-field rules, no show/hide logic.
  • Lookups and integrations. Dropdown options are fixed in the spec; nothing calls another system.
  • Processes and tasks. The app has one service that a user launches by URL. There is no BPD, no task routing and no approvals between people.
