Service and interface

On Cloud Pak for Business Automation, BAW exposes its REST interfaces under the /bas gateway path of the Cloud Pak URL. The API explorer at /bas/bpm/explorer is Swagger UI: it reads the specification named in its ?url= query parameter and otherwise loads /bas/bpm/docs. The three explorer links therefore point at three Swagger 2.0 documents, which can be fetched directly as JSON by an authenticated caller.

Where the calls live

baw_ops.py holds every REST call the MCP tools make. react-coach/scripts/verify-service.mjs repeats the login and service lookup for the browser test. Without these settings, the build tools still work and the server tools say so.

How we got there

The endpoint set came from reading the three specifications against what each MCP tool needs, then checking the doubtful points with read-only calls against this cluster.

1 · Read the specs, not the explorer page

The explorer HTML is a generic Swagger UI shell: its script reads ?url= or falls back to <context>/docs. Fetching /bas/ops/docs, /bas/bpm/docs and /bas/case/docs with a bearer token returns the raw Swagger 2.0 JSON, which is what the tables on this page are counted from.

2 · Authentication: bearer token instead of the documented basic auth

All three specs declare only HTTP basic authentication. On Cloud Pak, the /bas gateway also accepts a Cloud Pak bearer token, and POST /icp4d-api/v1/authorize issues one from either a password or a Platform API key. We chose the bearer token because:

  • it supports BAW_APIKEY, which basic auth cannot;
  • the same token works as the ibm-private-cloud-session cookie, so the browser test logs in without going through the Cloud Pak login page.

Basic auth with a password also returned 201 from /bas/ops/system/login on this cluster, so it remains an option for password-only setups.

3 · CSRF token from /system/login

Every Ops and BPM operation lists a required BPMCSRFToken header. The token comes from POST /system/login, which exists in both the Ops and BPM specs and returns {csrf_token, expiration}. We request the documented maximum lifetime of 7200 seconds and send the token on every call. A GET /containers without the header still returned 200 here, but the header is documented as required, so we always send it.

4 · Apps and snapshots from the Ops containers routes

GET /std/bpm/containers lists process apps and toolkits (80 on this server). GET /std/bpm/containers/{container}/versions lists snapshots. The {version} path parameter of the export route is documented as "the acronym of the snapshot", which is the version field, not the display name in version_name. That is why the tools accept either value from the user but always pass version to the API.

5 · Export with or without the system toolkits

The export route returns the .twx as application/octet-stream. Its format parameter can skip system toolkits (twxWithoutToolkits). export_app leaves it unset, so you get the complete file. create_app sets it when it exports a base app: only that export's packaging metadata is used. A generated app is itself in the no-toolkits format, built from server/app_template.py: META-INF/package.xml names the System Data and UI Toolkit versions, and properties.json says {"twxWithoutToolkits":"true"}. twx_clone.py and modernize_coaches.py keep the IDs of toolkit objects that the app refers to but does not hold, with or without toolkits/*.zip.

6 · Install is asynchronous

POST /std/bpm/containers/install takes the file as the multipart form field install_file and answers 202 with a url pointing at /system/queue/{id} (with its authorization key query parameter). The code rebases that URL onto the /bas/ops gateway path and polls it every 5 seconds for up to 15 minutes until state leaves pending/running. The spec lists the final states as success and failure.

7 · Run URLs: why the older BPM REST API

Documented · GET /bas/bpm/exposed-services

Does not fit
  • The type parameter is required, and its only allowed value is rest. Omitting it returns 400 CWTBG0011E.
  • With type=rest it returned 5 items with only name, description, type, container, definitionUrl: no run URL, no snapshot, and no human services.

Used · GET /bas/rest/bpm/wle/v1/exposed/service

Current design
  • Returned 144 exposed items (140 URL services, 4 dashboards) across all apps and snapshots.
  • Each item carries processAppAcronym, display, snapshotName, tip and runURL, which is exactly what list_services and test_service need.
  • It is the older BPM REST API, so it is not in any explorer document.

Kept until the documented API can list human services with run URLs.

8 · Case REST reviewed and not used

The Case API deploys and operates case solutions. The MCP tools only build and modernize process apps. Ops containers/install already covers case solutions too (through its caseDosName, caseProjectArea and caseOverwrite parameters), so a future case feature would not need a separate install route.

Authentication flow

POST /icp4d-api/v1/authorize      { username, password | api_key }
     →  { token }                                 # Cloud Pak bearer token

POST /bas/bpm/system/login        Authorization: Bearer <token>
                                  { requested_lifetime: 7200 }
     →  201 { csrf_token, expiration }

every REST call                   Authorization: Bearer <token>
                                  BPMCSRFToken: <csrf_token>

browser (test_service)            cookie ibm-private-cloud-session=<token>
                                  + Authorization: Bearer <token>
  • Settings come from the environment first, then .env. Tokens stay in the server process and are never returned to the agent.
  • The login_request schema marks refresh_groups as required. We send only requested_lifetime, and the server still answers 201. Adding "refresh_groups": false would match the documented contract.
  • The MCP server logs in once, on the first tool call that needs the server, and reuses the tokens for the life of the process. The CSRF token lasts at most 7200 seconds.

Certificate verification is off.

Both baw_ops.py and verify-service.mjs skip TLS verification so they work against test clusters with self-signed certificates. That is acceptable for a TechZone test server and not for production.

Outstanding actions

  1. Re-authenticate on expiry. The cached tokens are never refreshed, so a long-running MCP session will start failing after the CSRF token's 2-hour lifetime. Retrying once with a fresh login on 401/403 would fix it.
  2. Follow next on paged lists. containers and versions return next/previous links; the code reads only the first page. All 80 apps came back in one page here, but a larger server could hide apps or snapshots.
  3. Send refresh_groups: false in the login body to match the documented schema.
  4. Track the run-URL dependency. /bas/rest/bpm/wle/v1/exposed/service is outside the published specs; check it on each BAW upgrade, or move to a documented route if one starts returning human services with run URLs.
  5. Settle certificate trust before pointing the tools at anything other than a test cluster.
